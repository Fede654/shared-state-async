# Post-expiry v2 — preregistration for the production-parameter collection (HRM-149)

Status: **POST-PILOT, PRE-CONFIRMATORY preregistration.** Written and
committed after the Phase 1–3 pilots (decoder validation, passive
smoke, capture-on/off equivalence, topology shakedown, driver
machinery tests) and **before any confirmatory run**. Pilot data
existed when this was written; every pilot run is listed in §8 and is
excluded from confirmatory analysis. This document governs the runs in
the frozen schedule of §2 and nothing else. Deviations, if any, must
be reported as deviations.

This is an honest improvement over the v1 analysis (plan specified
mid-collection, amendments post-outcome — recorded there as NOT
preregistration). It is still not "preregistration before any
collection": the pilots came first, by design.

## 1. Question and design

Does expired-author resurrection occur at PRODUCTION shared-state
parameters without any observation load? All confirmatory runs are
**passive** (zero probes, zero host connections; observation is packet
capture only, accepted as non-invasive by the pre-committed
equivalence gate — §8.3). Production registration: update interval
**30 s**, bleach TTL **2400 s** → authored insert TTL **2431 s**
(`app/shared_state_cli.cc:66`). Window: **7293 s = 3 lifetimes** per
run. Cell otherwise as v1 Cell A: 5 nodes, ±400 ms delay, 512 kbit/s,
25-entry bulk payload, staggered clocks, single publish (gen 1) and
never again.

## 3. Binary and topology decisions (made here, in advance)

- **Primary binary: v1 master only.** The production fleet runs v1;
  `merge_with_version` is not deployed, and mixed-fleet/branch
  questions belong to HRM-152/HRM-150. **No second binary in this
  collection** — "if wall clock allows" is discretionary sampling and
  is hereby ruled out. Each record stamps the binary sha256 at run
  time via the coupled provenance path (build at freeze:
  `b5b3de0a2703ce03…`, the reproduction-pinned v1 binary).
- **Primary topology: chain** (n=6; comparability with the entire v1
  evidence base). Ring and chord are **exploratory** (n=2 each):
  reported descriptively, no confirmatory claim, never pooled with
  chain.

## 4. Endpoints and estimands

Witness definitions are exactly the amended plan's, wire-derived and
outbound-only (author's completed, frame-acknowledged, non-host
outbound slices from the author's own pcap): outbound
absence→presence under single publish, and strict outbound TTL
increase (later > earlier). Denominators are PLANNED counts; invalid
runs shrink the numerator's evidence base and are reported, never
replaced.

- **Q1 (primary):** proportion of valid chain-passive runs with
  witness_count ≥ 1. Denominator: **6 planned**. Wilson 95% interval;
  the statistical unit is the RUN — packets, exchanges and witness
  events within a run are correlated and are never counted as
  replicates.
- **Q2 (secondary, descriptive):** per valid run, witness count and
  the measured number of completed gossip exchanges per lifetime
  (from the frame table; the nominal 80 = 2431/30 is reported beside
  the measured value, which is authoritative).
- **Q3 (secondary):** late recurrence — witnesses with t > 2 lifetimes
  after publish, per valid run; interpretable only where the
  end-of-window outbound-coverage gate holds. Bounds observed late
  recurrence; does not establish self-limitation.
- **Exploratory:** the same descriptives for ring and chord runs,
  reported per topology, no pooling.

No hypothesis tests. No pooling across topologies, TTL strata, or
with any v1/pilot data.

## 5. Validity (fail-closed, decided per run before any endpoint is read)

A run is **valid** iff acquisition-side `record_valid_acquisition`
(deps stable; supervisor clean — every daemon and capturer alive
throughout, capture attached before daemons, stopped after them) AND
wire-side `decode_valid` (zero kernel drops; no reassembly gaps;
recorded pcap hashes match; wire-confirmed propagation to every node
before author expiry; end-of-window outbound coverage; observed edge
set == declared edge set, both directions). Invalid runs are reported
with reasons and are **not** re-run, replaced, or substituted —
whatever the outcome looks like.

Infrastructure failures that produce no record are logged
(`*.FAILED.log`) and reported as no-record slots.
